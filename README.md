# shrink

Unix-фільтр без стану: читає код або текст зі stdin, стискає його для контексту LLM і одразу віддає в stdout наступній програмі. Працює локально, без мережі й без виклику моделі.

```bash
files-to-prompt docs | shrink --level 3 --stats | llm "що тут головне?"
```

[![CI](https://github.com/Ki-mik0/Shrink/actions/workflows/ci.yml/badge.svg)](https://github.com/Ki-mik0/Shrink/actions/workflows/ci.yml)

> Статус: етап 1 (базове CLI-ядро) завершено. Є режим `text`; режим `code` для Python, переклад any→en та обгортка для агентів — на етапах 2–3, див. [docs/PLAN.md](docs/PLAN.md).

## Встановлення

```bash
python -m venv .venv
.venv/Scripts/activate        # Linux/macOS: source .venv/bin/activate
pip install -e ".[dev]"       # + інструменти розробки
pip install -e ".[tokens]"    # опційно: точний підрахунок токенів через tiktoken
```

Глобальна команда (коли буде потрібна): `pipx install .`

## Використання

```bash
cat notes.md | shrink                    # режим text, рівень 2
cat notes.md | shrink -l 3 --stats       # максимальне стиснення + статистика в stderr
shrink --list-modes                      # доступні режими
shrink --mode-help text                  # що саме робить режим на кожному рівні
```

| Прапорець | Що робить |
| --- | --- |
| `-m, --mode` | режим стиснення (зараз — `text`); кілька режимів через кому (`a,b`) виконуються по черзі |
| `-l, --level` | 1 — легкий, 2 — середній (типовий), 3 — лише структура |
| `--format` | формат упакованого входу: `auto` (типово), `none`, `files-to-prompt`, `cxml`, `repomix-xml`, `repomix-markdown`, `repomix-plain` |
| `--delimiter REGEX` | новий файл починається з кожного рядка, що збігається з REGEX (іменована група `path` = ім'я файлу); перекриває `--format` |
| `--diff` | unified diff кожного файлу в stderr (без префікса, тож `2> changes.diff` дає придатний файл), а потім звіт `--stats`; рамка файлів у diff не потрапляє |
| `--stats` | токени до/після і відсоток у stderr (разом із рамкою файлів) та рядок на кожен крок: скільки зекономив кожен метод; без tiktoken — оцінка «символи / 4», позначена `~` |
| `--debug` | трейсбек при внутрішній помилці |
| `-V, --version`, `-h, --help` | версія, довідка |

### Режим `text`

| Рівень | Що прибирає |
| --- | --- |
| 1 | пробіли в кінці рядків, зайві порожні рядки |
| 2 | + повтори пробілів усередині рядка (відступи лишаються), дублікати абзаців від 20 символів (заголовки не чіпаються) |
| 3 | + HTML-коментарі й теги, Markdown-посилання й зображення → їхній текст, горизонтальні лінії |

Fenced-блоки коду (```` ``` ````, `~~~`) на рівнях 2–3 не змінюються, inline-код на рівні 3 теж. Чистий CRLF-вхід лишається CRLF.

Приклад на [tests/fixtures/messy.md](tests/fixtures/messy.md) (текст, скопійований з HTML-документації):

| Рівень | Токени (оцінка) | Економія |
| --- | --- | --- |
| 1 | ~176 → ~175 | −0,6% |
| 2 | ~176 → ~131 | −25,6% |
| 3 | ~176 → ~69 | −60,8% |

На вже охайному Markdown (наприклад, документ плану) економія мала: −2,6% на рівні 3.

### Скільки зекономлено і чим

```text
$ cat notes.md | shrink -l 3 --stats > /dev/null
shrink: stats: 1 document, tokens ~7 -> ~3 (-57.1%) [approx]
shrink:   whitespace         ~7 -> ~7 (+0.0%, +0.0% of input)
shrink:   spaces+duplicates  ~7 -> ~6 (-14.3%, -14.3% of input)
shrink:   markup             ~6 -> ~3 (-50.0%, -42.9% of input)
```

Рівні режиму `text` накопичувальні, тому кожен рядок показує внесок одного кроку: токени на вході й виході кроку, зміну в ньому та частку від усього входу. Підсумок по всіх файлах потоку сумується.

### Упакований вхід (files-to-prompt, Repomix)

Якщо на вході кілька файлів, shrink розпізнає формат за першими рядками, стискає **вміст кожного файлу окремо**, а рамку (заголовок із шляхом, `---`, `</file>`, преамбулу й епілог) повертає байт у байт. Без стиснення розбиття й склеювання відтворюють вхід точно, для будь-якого тексту (це перевіряють property-тести). Якщо формат не розпізнано, вхід лишається одним документом.

```bash
files-to-prompt src | shrink --level 2
files-to-prompt --cxml src | shrink
repomix --stdout | shrink --stats
```

Файли з розширенням коду (`.py`, `.js`, `.json`, …) у режимі `text` отримують лише рівень 1: вищі рівні прибирають «повторювані абзаци» й теги, а це змінює зміст коду. Для коду буде окремий режим `code` (етап 2b).

### Поведінка в пайпі

| Ситуація | Результат | Код виходу |
| --- | --- | --- |
| успіх, порожній вхід | вихід у stdout | 0 |
| отримувач закрив пайп (`\| head`) | тихий вихід | 0 |
| файл не вдалося стиснути | файл без змін + попередження в stderr | 0 |
| внутрішня помилка | один рядок у stderr (трейсбек — з `--debug`) | 1 |
| неправильний прапорець | повідомлення Click | 2 |
| Ctrl+C | без трейсбеку | 130 |

Вхід читається як байти й декодується UTF-8 з `surrogateescape`, тож невалідні байти проходять без втрат. Однаковий вхід дає байт-у-байт однаковий вихід.

## Розробка

```bash
pytest                 # тести + покриття (поріг 85%)
ruff check . && ruff format --check .
mypy
```

Структура: `src/shrink/` — `cli.py` (Click), `pipeline.py` (reader → splitter → compressor → writer), `compressors/` (режими + реєстр з лінивим імпортом), `io/`, `splitting/`, `observability/stats.py`. Новий режим — це новий модуль у `compressors/` і один рядок у `registry.py`.

### Час старту (NFR-1)

Базовий замір, Windows 11, Python 3.12, медіана з 15–20 запусків:

| Команда | Час |
| --- | --- |
| `python -c pass` | ~110 мс |
| `python -c "import argparse"` | ~144 мс |
| `python -c "import click"` | ~228 мс |
| `python -m shrink -V` | ~273 мс |
| `shrink.exe -V` | ~310–340 мс |

На цій машині сам інтерпретатор із лаунчером `shrink.exe` займає ~175 мс, тому ціль 150 мс на Windows недосяжна з будь-яким фреймворком; Click додає ще ~118 мс. На Linux замір робить job `startup` у CI (hyperfine).
