# Оцінювання shrink

Чотири частини. Перші три відтворюються повністю й без моделі:

1. **Стиснення:** скільки shrink економить у порівнянні з Repomix і skim.
2. **Переклад:** скільки токенів дає `--translate` для різних мов.
3. **Час старту** (NFR-1).
4. **Якість:** чи не гіршає від стиснення відповідь моделі (eval через безкоштовні моделі OpenRouter).

## 1. Стиснення: shrink проти Repomix і skim

```powershell
python eval/bench_compression.py            # лише shrink
python eval/bench_compression.py --others   # + Repomix 1.19.0 і skim 3.3.0 через npx (потрібен Node.js)
```

Потрібен словник токенізатора (`shrink --download tokenizer`): токени рахуються точно (o200k_base). Корпус описано в [corpus.py](corpus.py): 10 модулів stdlib того Python, що запускає скрипт (версія пишеться в результат), увесь код shrink, українські README і план, лог pytest з ANSI-кольорами ([corpus/pytest.log](corpus/pytest.log)) і JSON зі списком пакетів ([corpus/packages.json](corpus/packages.json)). Для кожного Python-файлу перевіряється, чи вивід ще розбирається `ast.parse`.

Результат на Python 3.12.10 ([results/compression.md](results/compression.md)), 33 файли, 115 273 токени:

| Інструмент | Токени | Зміна | Валідний Python |
| --- | ---: | ---: | ---: |
| shrink L1 (коментарі) | 98 110 | −14,9% | 33/33 |
| shrink L2 (+ докстрінги) | 85 206 | −26,1% | 33/33 |
| **shrink L3 (скелет)** | **26 529** | **−77,0%** | **33/33** |
| skim `structure` | 36 292 | −68,5% | 33/33 |
| Repomix `--compress` | 62 227 | −46,0% | 0/33 |
| skim `signatures` | 11 156 | −90,3% | 0/33 |

Серед інструментів, що лишають код валідним, shrink L3 стискає найсильніше. Сильніше стискає лише skim `signatures`, але його вивід уже не Python. Repomix вставляє між фрагментами роздільник `⋮----`, тому жоден файл не розбирається.

Інші типи (той самий звіт): лог pytest −38%, JSON −22% без втрат (рівень 1) і −93% з обрізанням масивів (рівень 2), «брудний» Markdown −23…−68%; на охайному українському тексті форматування майже нема чого прибирати (−0…−8%) — там економію дає переклад (`--translate`).

## 2. Переклад: скільки токенів дає `--translate` для різних мов

```powershell
python eval/bench_translate.py      # потрібні [translate], --download translate і --download tokenizer
```

Однакові 4 технічні абзаци 10 мовами ([corpus/parallel.json](corpus/parallel.json)). Англійський текст написано для бенчмарку, інші мови переклала LLM (Claude), і їх лишено як є. Inline-код, шлях, URL і числа однакові в усіх мовах, тож заодно перевіряється захист. Результат ([results/translate.md](results/translate.md)):

| Мова | Токени | Відносно англійської | Після `--translate` | Економія | Перекладено абзаців | chrF до англ. еталона |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| англійська | 146 | 1,00× | 146 | 0% | 0/4 | 100 |
| **українська** | 214 | **1,47×** | 145 | **−32,2%** | 4/4 | 77 |
| польська | 203 | 1,39× | 144 | −29,1% | 4/4 | 77 |
| японська | 213 | 1,46× | 161 | −24,4% | 3/4 | 60 |
| арабська | 181 | 1,24× | 145 | −19,9% | 4/4 | 76 |
| французька | 174 | 1,19× | 143 | −17,8% | 4/4 | 75 |
| німецька | 163 | 1,12× | 144 | −11,7% | 4/4 | 86 |
| іспанська | 157 | 1,08× | 142 | −9,6% | 4/4 | 79 |
| китайська | 148 | 1,01× | 141 | −4,7% | 2/4 | 46 |
| російська | 154 | 1,05× | 150 | −2,6% | 2/4 | 49 |

- **Економія росте разом із «податком токенізатора».** Мова, яку o200k кодує гірше, дає більший виграш від перекладу: для української 1,47× обертається на −32%.
- **Українська проти російської.** o200k кодує російську майже як англійську (1,05×), а українську в 1,47 раза дорожче. Це той самий «Ukrainian penalty», що й у [arXiv 2601.13328](https://www.arxiv.org/pdf/2601.13328).
- **Правило «лише якщо дешевше» працює.** Для російської й китайської переклад часто не зменшує кількість токенів, тож половина абзаців лишилася в оригіналі. Низький chrF для цих мов — наслідок саме цього: з англійським еталоном порівнюються неперекладені абзаци.
- **Якість NLLB не бездоганна.** В арабській «tool» стало «device», а «run» перетворилося на «turn on». Тому переклад — опція, а не типова поведінка.

## 3. Час старту (NFR-1)

```powershell
python eval/bench_startup.py
```

Windows 11, Python 3.12.10, медіана з 20 запусків ([results/startup.md](results/startup.md)):

| Команда | Медіана, мс | Понад `python -c pass`, мс |
| --- | ---: | ---: |
| `python -c pass` | 105 | — |
| `python -m shrink -V` | 246 | +140 |
| `echo text \| python -m shrink` | 253 | +147 |
| `echo text \| shrink` (лаунчер `shrink.exe`) | 292 | +186 |
| `echo text \| python -m shrink --stats` | 760 | +654 |

- **Абсолютна межа недосяжна на Windows.** Один лише інтерпретатор стартує за 105 мс, тож 150 мс тут не вкластися.
- **Відносна межа «≤ 150 мс понад інтерпретатор»** виконується через `python -m shrink` (+147 мс), а через лаунчер `shrink.exe` ні (+186 мс): лаунчер сам додає ~40 мс.
- **Найдорожчий імпорт — Click**, ~68 мс із ~140 (на Windows він ще й тягне `ctypes` для консолі). Заміна Click на `argparse` скоротила б старт приблизно на 50 мс.
- **`--stats` повільніший,** бо завантажує tiktoken і словник: +0,5 с.
- **Linux міряє CI.** На Linux інтерпретатор стартує в кілька разів швидше, і ці цифри дає job `startup` (hyperfine): таблицю видно в підсумку запуску на вкладці Actions.

## 4. Якість: чи відповідає модель так само добре

```powershell
$env:OPENROUTER_API_KEY = "sk-or-..."       # ключ з https://openrouter.ai/keys
python eval/run_quality.py --dry-run          # розміри промптів, без мережі
python eval/run_quality.py                    # прогін
python eval/run_quality.py --report           # лише перебудувати таблицю
```

- **Питання.** [quality/questions.json](quality/questions.json): 24 питання до трьох корпусів (textwrap/shlex/fnmatch, пакет `json`, частина коду shrink). Відповіді звірено з кодом. Кожне питання позначене, де лежить відповідь: у сигнатурі чи коді модуля (скелет це зберігає) або в тілі функції (рівень 3 це прибирає).
- **Варіанти контексту.** Оригінал, `code` рівнів 1, 2 і 3, а також рівень 3 з `--query` (запит — текст питань: функції, яких вони стосуються, лишаються з тілом).
- **Оцінка.** За ключовими словами з еталону, без LLM-судді: безкоштовно й відтворювано.
- **Безкоштовний тариф OpenRouter.** Обмеження: 20 запитів на хвилину, 50 на день без кредитів. Тому всі питання корпусу йдуть одним запитом: 3 корпуси × 5 варіантів × 3 прогони = **45 запитів**, вартість $0. Між запитами пауза 3,5 с. Кожна відповідь зберігається в `results/raw/`, тож при `429` прогін можна продовжити наступного дня.
- **Модель.** Типова `nvidia/nemotron-3-ultra-550b-a55b:free`, інша задається через `--model`. Моделі Gemma `:free` обслуговує лише Google AI Studio, і вони часто «temporarily rate-limited upstream». Скрипт тоді чекає 30, 60, 120 і 240 с, а якщо модель і далі зайнята, акуратно зупиняється: збережені відповіді лишаються, і той самий запуск пізніше продовжить роботу. Безкоштовні провайдери можуть зберігати промпти, але корпус складається лише з публічного коду.

### Результат

Модель `nvidia/nemotron-3-ultra-550b-a55b:free`, 3 прогони на варіант, 45 запитів, $0 ([results/quality.md](results/quality.md); сирі відповіді — у [results/raw/](results/raw/)):

Токени — увесь промпт (файли й питання), точний o200k_base:

| Контекст | Токени | Зміна | Точність | Питання про структуру | Питання про тіла функцій |
| --- | ---: | ---: | ---: | ---: | ---: |
| оригінал | 24 784 | — | 100% | 100% | 100% |
| L1 (коментарі) | 22 582 | −8,9% | 100% | 100% | 100% |
| L2 (+ докстрінги) | 16 680 | −32,7% | 100% | 100% | 100% |
| L3 (скелет) | 6 044 | −75,6% | 85% | 100% | 39% |
| L3 + `--query`, спершу | 10 139 | −59,1% | 92% | 100% | 67% |
| L3 + `--query`, після виправлення | 13 291 | −46,4% | 100%* | 100%* | 100%* |

\* 2 з 3 корпусів (textproc і json): прогін корпусу shrink перервав денний ліміт OpenRouter, і `python eval/run_quality.py` його допитає.

Висновки:

- **Рівні 1–2 якості не знижують.** Модель відповіла на всі питання з контексту, меншого на третину.
- **Рівень 3 зберігає все про структуру.** Сигнатури, значення за замовчуванням, базові класи й константи модуля розпізнаються на 100%. Втрачається лише те, що лежить у тілах функцій (39%), і на це скелет свідомо йде.
- **`--query` повертає знання про тіла функцій.** Спершу лише частково: точність на таких питаннях зростала з 39% до 67%. Причина була в тому, що запитом служив текст усіх восьми питань корпусу разом, і BM25 оцінює фрагменти відносно найкращого бала. Тож питання з найрідкіснішими словами забирали верх, а функції для `a4` і `a7` (`shlex.quote`, `shlex.join`) не дотягували до порогу «половина від найкращого». Тепер кожне питання запиту (речення до `.`, `?`, `!` або `;`) ранжується окремо, і фрагмент отримує найкращу оцінку серед питань. Це коштує +3 152 токени (+31%), але дає 100% на прогнаних корпусах при −46% від оригіналу. Відповіді першого варіанту лишаються в `results/raw/.../previous/`.
- **Модель не вигадує.** Усі 17 хибних відповідей — чесне «unknown»: коли тіла функції в контексті немає, модель так і каже.
- **Про лічбу токенів.** Перший прогін записав токени оцінкою «символи / 4», бо в тому середовищі не знайшовся словник токенізатора. Тепер звіт перераховує токени сам і точно, а скрипт попереджає, якщо точного токенізатора немає.

## 5. Велика задача з довгою відповіддю: todo + авторизація

```powershell
python eval/run_generation.py --dry-run    # розміри промптів, без мережі
python eval/run_generation.py              # 6 запитів (по одному на варіант)
python eval/run_generation.py --runs 3     # ще прогони, щоб усереднити вихід
python eval/run_generation.py --runs 3 --variants original,L3,L3+brief  # лише ці варіанти
python eval/run_generation.py --runs 3 --variants L3+no-docs+brief
python eval/run_generation.py --report     # лише перебудувати таблицю
```

Модель отримує реалістичний стартовий проєкт ([generation/starter/](generation/starter/), FastAPI + чистий JS, 10 774 токени) і задачу ([generation/task.md](generation/task.md)): акаунти й особисті списки справ, від міграції БД до сторінок фронтенду. Відповідь займає тисячі токенів.

У стартовому проєкті вже є все, що треба повторно використати: `get_db`, міграції, хешування паролів, токени, `get_current_user`, `ApiError`, пагінація, `apiFetch`. Тож модель має зрозуміти ці API з контексту, який стискає shrink. Проєкт надсилається в тих самих п'яти варіантах, що й в eval якості (для L3+query запит — текст задачі), і в шостому: L3 + `--brief`, тобто L3 з короткою вказівкою відповідати стисло. Вона спрямована на вихідні токени, яких стиснення контексту не торкається.

Кожна відповідь зберігає хеш свого промпту. Коли shrink змінюється і промпт варіанта вже інший, наступний запуск відкладає стару відповідь у `previous/` і питає модель знову; у звіті такі рядки до перезапиту позначені `(stale)`.

Для кожної відповіді записується:
- вхідні токени: точний o200k і те, що порахував провайдер;
- вихідні токени;
- чи відповідь обрізано (`finish_reason = length`);
- час;
- повнота без запуску коду: 12 перевірок (файли роутерів і сторінок, міграція `todos`, реєстрація роутерів, `/register`, `/login`, `/me`, PATCH/DELETE, `get_current_user`, `paginate`, `apiFetch`), а також чи розбирається Python.

Шляхи з відповіді приймаються лише всередині `backend/` і `frontend/`. Згенерований код ніде не записується й не виконується.

Розміри промптів (dry run, точний o200k). Перший стовпчик — до режиму `web`, другий — з ним:

| Контекст | Без `web` | Зміна | З `web` | Зміна |
| --- | ---: | ---: | ---: | ---: |
| оригінал | 11 556 | — | 11 556 | — |
| L1 | 11 438 | −1,0% | 11 086 | −4,1% |
| L2 | 9 063 | −21,6% | 8 148 | −29,5% |
| L3 | 7 217 | −37,5% | 5 114 | **−55,7%** |
| L3 + `--query` | 8 939 | −22,6% | 8 606 | −25,5% |
| L3 + `--brief` | — | — | 5 161 | −55,3% |

Майже половина проєкту — JS, HTML, CSS і README. У першому прогоні shrink стискав їх лише на рівні пробілів і розмітки, тож вхід на L3 зменшився на 37,5% проти −76% на чистому Python (розділ 4). Режим `web` прибирає коментарі й JSDoc, мініфікує CSS, а на рівні 3 зводить функції JS до сигнатур і CSS до селекторів та змінних; фронтенд стискається з 3 013 до 890 токенів. Тепер найбільший нестиснутий шматок — README з правилами проєкту (1 091 токен): це проза, яку модель має прочитати повністю. `--query` і далі стискає слабко, бо задача згадує майже всі хелпери проєкту, і BM25 лишає їх цілими.

### Скільки треба для −40% усього запиту

Вихідні токени (~9 тис.) — 44% суми, і стиснення контексту їх не зменшує. Навіть якби вхід зник повністю, сума впала б лише на 56%. Щоб уся сума зменшилась на 40%, тобто до 12 353 токенів, при вході L3 + `--brief` (5 161) вихід має бути не більше 7 192 токенів, на 20% менше за оригінал. Тому `--brief` просить модель не писати коментарів і докстрінгів у новому коді, не пояснювати і не повторювати файли без змін. Вимоги задачі лишаються ті самі, і перевірки повноти показують, чи не постраждала відповідь.

### Другий прогін (режим `web` і `--brief`)

Та сама модель, по одному прогону. Оригінал не перепитувався: його промпт не змінився.

| Контекст | Вхід | Економія входу | Вихід | Усього | Економія всього | Обрізано | Повнота |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| оригінал | 11 556 | — | 9 032 | 20 588 | — | 0/1 | 100% |
| L1 | 11 086 | −4,1% | 8 606 | 19 692 | −4,4% | 0/1 | 100% |
| L2 | 8 148 | −29,5% | 8 111 | 16 259 | −21,0% | 0/1 | 100% |
| L3 | 5 114 | −55,7% | 16 000 | 21 114 | +2,6% | **1/1** | 50% |
| L3 + `--query` | 8 606 | −25,5% | 8 916 | 17 522 | −14,9% | 0/1 | 100% |
| L3 + `--brief` | 5 161 | −55,3% | 7 641 | 12 802 | **−37,8%** | 0/1 | 92% |

- **`--brief` працює:** вихід на 15% коротший за оригінал (7 641 проти 9 032), і разом із входом це −37,8% усього запиту, близько до мети −40%. Єдина пропущена перевірка — модель поклала JS сторінок у вбудовані `<script type="module">` в HTML (там `apiFetch` використано правильно), а файли `js/login.js` і `js/todos.js`, яких вимагає задача, лишила порожніми.
- **L3 знайшов ваду режиму `web`.** Тіла JS-функцій ставали `{}`, і модель прочитала це як порожню реалізацію: «the functions are empty. I need to implement them properly». Вона заново написала `api.js` і `ui.js`, кілька разів переписала `auth.py` і вперлася в ліміт 16 000 токенів, так і не дописавши сторінки. У Python такої проблеми немає, бо `...` — загальновідомий знак пропущеного тіла. Тепер пропущене тіло в JS позначається `{/* ... */}` (порожнє тіло лишається `{}`), що коштує +22 токени на весь проєкт. Цим промптом L3 і L3 + `--brief` треба запитати ще раз.

Перезапит із позначкою: **L3 −55,6% входу, вихід 7 900, −36,7% усього, повнота 100%**, без обрізання і без переписаних хелперів, тож позначка спрацювала. А L3 + `--brief` цього разу вперся в ліміт: модель видала всі 9 файлів (~9 тис. токенів), а потім без пояснень почала видавати вже готові `todos.html`, `index.html`, `login.html`, `auth.py` знову, щоразу довшими. Той самий збій (повторна видача написаних файлів) був і в обрізаному L3 до виправлення. Тому:
- у `--brief` додано речення «Give each file once, complete and final; never rewrite a file you already gave» (+20 токенів, разом ~65);
- вихід однієї й тієї ж моделі на однаковий за змістом промпт коливається від 7,6 до 16 тис. токенів, тож одного прогону мало. Для оригіналу, L3 і L3 + `--brief` потрібно `--runs 3` (`--variants original,L3,L3+brief`, 7 запитів).

### Три прогони: оригінал, L3, L3 + `--brief`

Середнє за трьома прогонами (вихід — як порахував провайдер, обрізані відповіді враховано повністю):

| Контекст | Вхід | Економія входу | Вихід | Усього | Економія всього | Обрізано | Повнота |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| оригінал | 11 556 | — | 8 846 | 20 402 | — | 0/3 | 100% |
| L3 | 5 136 | −55,6% | 10 556 | 15 692 | −23,1% | 1/3 | 92% |
| L3 + `--brief` | 5 200 | −55,0% | 7 703 | 12 903 | **−36,8%** | 0/3 | 97% |

- **Головне, що дає `--brief`, — модель не зациклюється.** Без нього L3 у 2 з 4 прогонів почав видавати вже написані файли знову й вперся в ліміт (у 3-му прогоні цієї серії — так само). З `--brief` усі три відповіді завершилися: 7,6–7,8 тис. токенів. Незациклені відповіді L3 і L3 + `--brief` майже однакові за довжиною (~7,8 проти ~7,7 тис.).
- **Вказівку «без докстрінгів» модель ігнорує:** у кожній відповіді ~20 докстрінгів, як і без `--brief`. Модель копіює стиль контексту, а L3 лишає однорядкові докстрінги. Ще одна деталь: з `--brief` модель міркує довше (430–540 токенів reasoning проти ~220), і вони теж рахуються як вихідні.
- **Що ще лишилося в контексті:** докстрінги й JSDoc займають ~950 із 4 467 токенів L3-контексту (21%). Звідси опція `--no-docs`: вона прибирає їх повністю, із перевіркою, що код не змінився. Вхід `L3 + --no-docs + --brief` — 4 270 токенів (**−63%**). Якщо вихід лишиться на рівні L3 + `--brief`, це близько −41% усього запиту; якщо модель, не бачачи докстрінгів, писатиме їх менше, — більше. Чи не впаде повнота без докстрінгів, покаже прогін (`--runs 3 --variants L3+no-docs+brief`, 3 запити).

### `--no-docs`: менший вхід, гірший результат

| Контекст (3 прогони) | Вхід | Економія входу | Вихід | Усього | Економія всього | Обрізано | Повнота |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| L3 + `--brief` | 5 200 | −55,0% | 7 703 | 12 903 | **−36,8%** | 0/3 | 97% |
| L3 + `--no-docs` + `--brief` | 4 270 | −63,0% | 9 659 | 13 929 | −31,7% | 0/3 | **67%** |

Без докстрінгів модель гірше розуміла хелпери проєкту. В одному прогоні вона почала міркувати вголос просто у відповіді («Wait, I need to import CurrentUser… Let me check the token structure»): 13 882 вихідних токени, 6,7 тис. символів прози між файлами, і бекенд недописаний. У двох інших вона не створила `js/login.js` і `js/todos.js`, а в одному ще й заново написала `api.js`, назвавши стиснуті тіла «placeholder». Тож докстрінги на рівні 3 — не баласт: однорядковий опис функції коштує ~15 токенів і економить моделі сотні токенів здогадок. `--no-docs` лишається в shrink як явна опція для задач, де модель лише читає код (огляд, питання про структуру), але для генерації коду не рекомендований.

### Підсумок: скільки shrink економить на великій задачі

Найкраща конфігурація — **`shrink --level 3 --brief`**: **−55% входу і −36,8% усього запиту** (середнє за 3 прогонами, розкид окремих прогонів −36,3…−37,2%), повнота 97%, жодної обрізаної відповіді.

До поставленої мети −40% бракує ~3 пунктів, і це межа без втрати якості:
- **Вхід уже стиснутий більш ніж наполовину.** Далі стискати можна лише прозу, яка допомагає моделі: докстрінги (`--no-docs`, див. вище) або README з правилами проєкту (1 091 токен).
- **Решта — це код, який модель мусить написати.** ~7 тис. токенів на 9 файлів — сама вимога задачі. Вихідні токени shrink може зменшити лише вказівкою, а модель виконує її частково: прибирає пояснення й повтори, але не докстрінги, які бачить у стилі проєкту.
- **Найбільший внесок `--brief` — стабільність:** без нього L3 у 2 з 4 прогонів зациклювався й вичерпував ліміт у 16 тис. токенів. Такий прогін коштує дорожче за оригінал.

Для задач «прочитай багато, відповідай коротко» (розділ 4) економія входу майже дорівнює економії всього запиту: там L3 дає −76%.

### До −45%: правки замість повних файлів

Розбір трьох відповідей L3 + `--brief` по файлах: ~28% виходу (~1 900 токенів) — це три файли, які вже існують (`db.py` ~970, `index.html` ~490, `main.py` ~450). Модель переписує їх повністю заради однієї міграції, двох `include_router` і двох посилань, бо задача вимагає «every new or changed file in full». Agent-інструменти (aider, Claude Code) так не роблять: вони передають лише правки.

Тому я спробував просити в `--brief` давати наявні файли блоками SEARCH/REPLACE, а якщо потрібних рядків не видно (тіло скорочене до `...`), то файлом повністю. Модель цитує те, що бачила, тобто стиснуту копію, тож `shrink.edits` шукає SEARCH спершу точно, а потім рядок за рядком, ігноруючи відступи, порожні рядки та рядки-коментарі справжнього файлу, і вирівнює відступ заміни. Правка, що не знайшлася або знайшлася кілька разів, не застосовується; eval рахує такі в стовпчику «Edits applied», а перевірки повноти й розбір Python ідуть по файлах після правок.

Вхід із такою вказівкою — 5 273 токени (−54,4%). Для −45% усього запиту вихід мав би бути не більше ~5 950 токенів.

**Результат (3 прогони): не спрацювало.** У двох прогонах модель не дала жодної правки, бо останній рядок задачі («Return every new or changed file in full») переважив вказівку, що стояла перед задачею. У третьому вона взяла заголовок `## Edit:`, але поклала під ним повні файли без блоків SEARCH, а потім зациклилася до 16 тис. токенів. Разом: −23,8% усього запиту і повнота 83%, гірше, ніж без цієї вказівки. Тому `--brief` повернуто до попереднього тексту, і рядок L3 + `--brief` у таблиці знову показує його три відповіді (−36,8%). Відповіді з правками збережено в `results/raw-generation/.../previous/L3_brief/0ee49bf79908823c/`. Архівація тепер кладе кожен промпт в окрему теку, бо раніше вона перезаписувала старіші відповіді.

**Остання спроба — `L3+brief+edits`.** Та сама вказівка про правки, але *після* задачі, як виняток із її формату. Саме туди її міг би дописати проксі `shrink wrap`, у кінець останнього повідомлення. Вхід — 5 288 токенів (−54,2%). Розділ `## Edit:`, у якому модель дала повний файл, eval зараховує як повний файл.

**Результат (3 прогони): гірше.** Після задачі модель правками користувалася (21 правка), але застосувалися лише 10, і реєстрацію роутерів не пройшов жоден прогін; один прогін знову зациклився. Разом −21,1% усього запиту і повнота 86%. Розбір невдалих правок показує принципову причину: у SEARCH модель копіює те, що бачила, тобто **стиснуту** копію файлу зі скороченими докстрінгами, тілами `...` і мініфікованим CSS. Таких рядків у справжньому файлі немає. А якби правка й знайшлася, заміна вставила б `...` замість справжніх тіл функцій. Правки й рівень 3 несумісні: модель не може безпечно правити код, якого не бачить. Без стиснення (рівні 1–2) правки мали б сенс, але тоді вхід зменшується лише на 4–30%.

**Підсумок спроб до −45%:** на цій моделі найкращий результат лишається за `--level 3 --brief`: −36,8% усього запиту при повноті 97% (3 прогони). Решта варіантів зменшували вхід ще більше, але модель від цього писала довше або гірше:

| Спроба | Вхід | Усього | Повнота |
| --- | ---: | ---: | ---: |
| L3 + `--brief` | −55,0% | **−36,8%** | 97% |
| L3 + `--no-docs` + `--brief` | −63,0% | −31,7% | 67% |
| L3 + правки (вказівка перед задачею) | −54,4% | −23,8% | 83% |
| L3 + `--brief` + правки після задачі | −54,2% | −21,1% | 86% |

### До −50%: скорочена відповідь (`--lazy`), компактні відступи (`--dedent`) і `shrink apply`

Невдача правок підказала інший підхід: якщо модель усе одно копіює стиснутий вигляд, хай копіює, а заповнює пропущене не вона, а `shrink apply` ([../src/shrink/restore.py](../src/shrink/restore.py)). Окремо видно ще одну проблему L3 + `--brief`: переписуючи наявні файли «повністю», модель **вигадує** тіла функцій, яких не бачила; у `main.py` першого прогону з'явився виклик `init_db(conn)` без імпорту. Перевірки повноти цього не ловлять.

- **`--lazy`** (вказівка після задачі, як виняток із її формату): наявний файл повертається так, як модель його бачила, із заглушками `...`/`{/* ... */}` для незмінних тіл і рядком `...` (`/* ... */`, `<!-- ... -->`) замість незмінних частин. Злиття йде за іменами (функції, класи, змінні, імпорти за модулем, HTML за `id`, CSS за селектором), а не за текстом, тож цитата скороченого вигляду його не ламає; частина, що збігається з будь-яким рівнем стисненого вигляду, береться з оригіналу дослівно. Перевірка: стиснений вигляд кожного з 13 файлів стартера (рівні 1–3, також у компактних відступах) відновлюється байт-у-байт.
- **`--dedent`**: Python з одним пробілом на рівень, JS/HTML/CSS без відступів, і в контексті, і (за вказівкою) у відповіді. На o200k це −5,7% токенів нового Python-коду, −8,7% JS і −11,4% HTML (виміряно на трьох відповідях L3 + `--brief`). Прибирання переносів рядків додало б лише ~1% (`";
"` — один токен), тож переноси лишаються.

Вхід: L3 + `--brief` + lazy — 5 316 токенів (−54,0%, вказівка коштує ~115), L3 + dedent + `--brief` + lazy — 5 200 (−55,0%: dedent заощаджує ~160 на контексті й коштує ~40 на вказівці).

**Прогноз до прогону** (три відповіді L3 + `--brief`, перераховані так, ніби модель виконала вказівки: наявні файли — лише змінені частини, тобто міграції, імпорт роутерів, `create_app` і навігація, новий код — у компактних відступах). Це оцінка зверху: модель може виконати вказівки гірше:

| Варіант | Вихід (прогноз) | Усього (прогноз) | Економія |
| --- | ---: | ---: | ---: |
| L3 + `--brief` (виміряно) | 7 703 | 12 903 | −36,8% |
| L3 + `--brief` + lazy | ~6 380 | ~11 690 | ~−42,7% |
| L3 + dedent + `--brief` + lazy | ~5 940 | ~11 140 | ~−45,4% |

Чому не −50%: навіть за ідеального виконання ~4 650 токенів виходу — це **новий** код (два роутери, дві сторінки і два скрипти), який модель мусить написати; з боку контексту його не стиснути. Ще ~500 токенів виходу — приховані reasoning-токени; на стиснутому контексті модель «думає» довше (430–540 проти ~285 в оригіналі). З `--reasoning none` для всіх варіантів прогноз ~−47%. Решта перевірених ідей дає крихти: імпорти, що лишилися невикористаними після скелетизації, −100 токенів; переноси рядків −30; відсікання розділів README за запитом не працює, бо задача з багатьох рядків робить релевантним майже все.

Прогін (6 запитів):

```bash
python eval/run_generation.py --runs 3 --variants L3+brief+lazy,L3+dedent+brief+lazy
```

Стовпчик «Restored» показує, у скількох файлах `shrink apply` щось заповнив, скільки файлів не вдалося злити і скільки функцій лишилися заглушками без оригіналу (недороблена відповідь, а не економія).

**Результат (3 прогони на варіант):**

| Варіант | Вхід | Вихід | Усього | Повнота |
| --- | ---: | ---: | ---: | ---: |
| L3 + `--brief` | −55,0% | 7 703 | −36,8% | 97% |
| L3 + `--brief` + lazy | −54,0% | 7 635 | −36,5% | 94% |
| L3 + dedent + `--brief` + lazy | −55,0% | 7 043 | **−40,0%** | 94% |

- **`--dedent` спрацював.** У всіх трьох прогонах модель писала Python з одним пробілом на рівень, а HTML і JS без відступів; усі 12 Python-файлів після `shrink apply` розбираються. Це новий найкращий результат на цій моделі: −40,0% усього запиту. Прогноз для цього кроку (≈−440 токенів нового коду) справдився приблизно наполовину, бо reasoning у варіанті з dedent коливався від 350 до 1 004 токенів.
- **`--lazy` модель проігнорувала (0 із 6 прогонів).** `db.py` і `main.py` вона щоразу повертала повністю, без жодної заглушки чи `...`, хоча вказівка стояла після задачі. Останній рядок формату задачі («complete file content») переважує, як і з правками. `shrink apply` усе одно приніс користь: ~11 незмінних частин на файл (докстрінги модуля й класів, коментарі) взято з оригіналу, тож у записаному файлі вони не загубилися.
- **Небезпечна знахідка:** переписуючи `db.py` «повністю», модель вигадує тіла функцій, яких не бачила (9 із ~11 у кожному прогоні відрізняються від справжніх). Наприклад, `schema_version()` у вигаданому вигляді читає іншу таблицю, ніж справжній код, і зламала б уже створену базу. Перевірки повноти цього не помічають. Це проблема рівня 3 як такого, з `--lazy` чи без нього: модель не може безпечно переписувати код, якого не бачила.
- Пропуск «frontend uses apiFetch» у 2 з 3 прогонів — та сама поведінка, що й у L3 + `--brief`: модель кладе JS сторінки всередину `todos.html`, а `js/todos.js` лишає порожнім.

Підсумок: на Nemotron найкраще — `--level 3 --brief --dedent`: −40,0% усього запиту при повноті 94%. До −50% бракує ~2 000 токенів; без виконання `--lazy` (його потенціал ~1 400 токенів) їх не набрати.

### Тести поведінки: чи працює застосунок

Перевірки повноти вище лише шукають файли й ключові слова. Колонка **Works** запускає відповідь: стартер плюс файли відповіді в тимчасовій теці, 21 перевірка за вимогами задачі через FastAPI `TestClient` ([generation/functional.py](generation/functional.py)). Одна з них відкриває новим кодом базу, створену кодом **стартера**, як на вже встановленій системі. Фронтенд перевіряється статично: сторінка підключає свій скрипт, а скрипт не порожній і викликає `apiFetch`. Код писала модель, тому він запускається в окремому процесі без ключів в оточенні, а audit hook забороняє підпроцеси, мережу (крім loopback) і запис поза текою. Тести доведено на еталонній відповіді ([../tests/fixtures/generation_reference.md](../tests/fixtures/generation_reference.md)): вона проходить 21/21 (`tests/unit/test_functional.py`).

```powershell
pip install -r eval/requirements-generation.txt
python eval/run_generation.py --report
```

**Результат на збережених відповідях Nemotron** (нових запитів не було):

| Варіант | Усього | Повнота (слова) | Works |
| --- | ---: | ---: | ---: |
| original | 100% (база) | 100% | **81%** |
| L1 / L2 | −3,5% / −20,3% | 100% | 33% / 38% |
| L3+query | −14,1% | 100% | 86% |
| L3 | −23,1% | 92% | 11% |
| L3 + `--brief` | −36,8% | 97% | **11%** |
| L3 + dedent + `--brief` + lazy | −40,0% | 86% | **11%** |

**Попередні висновки про якість на рівні 3 були хибними.** Майже жодна з цих відповідей не дає застосунку, що запускається. Причина одна: на рівні 3 `db.py` і `main.py` видно лише як сигнатури, а модель переписує їх «повністю» і вигадує тіла. Звідси `NameError: sqlite3`, `Cannot operate on a closed database`, `create_app()`, що вимагає `APP_SECRET` з оточення, і нова таблиця версій замість `PRAGMA user_version`, яка зламала б наявну базу. (Повнота тепер 86% замість 94%: для `+lazy`/`+dedent` рахується те, що записав би `shrink apply --context`, а він відхиляє вигадану `create_app()`, тому роутери в цих прогонах не зареєстровані.)

Оригінал теж не дає 100%. Це власні помилки моделі, і вони є в усіх прогонах: `login_failed` пишеться в аудит перед `raise`, тож `get_db` відкочує його; заголовок з самих пробілів приймається; скрипти сторінок вбудовані в HTML, а `js/*.js` порожні. **100% на Nemotron недосяжні навіть без стиснення.**

### Захист від вигаданого коду: `--keep`, `--patch`, `apply --context`

- `shrink apply --context` бере той самий текст, що бачила модель. Функція, яку вона бачила як `...`, лишає код стартера, хоч би що було у відповіді. На 6 збережених відповідях він відхилив по 8 вигаданих тіл у кожній.
- `--keep create_app` лишає видимою функцію, яку задача називає в коді (`` `create_app()` ``). Її нове тіло приймається.
- `--patch` просить для наявних файлів `## Patch:` лише зі зміненими означеннями.

Симуляція на старих відповідях (захист увімкнено, `create_app` вважається видимою, і в неї дописано два `include_router`): відповідь L3 + dedent №3 проходить **19/21** замість 3/21, тобто краще за оригінал (17/21). №2 — 16/21. Решта прогонів падає на власних помилках моделі в **нових** файлах (`audit`, `sqlite3` без імпорту), які є і на L1.

**Прогноз** для `L3+keep+dedent+brief+patch`: вхід 5 416 (−53,1%). Вихід — на відповідях Nemotron, де повні наявні файли (~1 720 токенів) замінено еталонними патчами (538):

| Умова | Усього проти оригіналу |
| --- | ---: |
| reasoning low (як досі) | ≈ −44,7% |
| без reasoning у всіх варіантах | ≈ −46,9% |

Це прогноз за умови, що модель виконає формат `## Patch:`. Вказівку `--lazy` вона проігнорувала, тому це треба перевірити прогоном. Для 100% Works потрібна модель, яка сама проходить тести без стиснення; її вибирає пілот:

```powershell
python eval/run_generation.py --model particle-ai/particle-1:free --reasoning none --variants original,L3+keep+dedent+brief+patch
```

Парсер брав лише перший блок, тож роутери не реєструвалися. Висновки:

- **Якість великої відповіді не впала.** На кожному рівні модель написала повний застосунок (9–10 файлів, усі 12 перевірок, Python розбирається). Хелпери стартового проєкту вона викликала правильно навіть зі скелета L3, тобто з самих сигнатур: `create_access_token(user_id, username, settings)` з правильним порядком аргументів, `Depends(page_params)`, `paginate(items, total, page)`, помилки через `ApiError` без жодного `HTTPException`, запити лише через `apiFetch`. Відхилень від правил проєкту два, обидва дрібні: L3+query зібрав конверт пагінації вручну замість `paginate`, а L3 один раз прочитав `innerHTML` (запису через `innerHTML` немає). Оригінальний контекст відхилень не дав. Код не запускався, тож ідеться про повноту й використання API, а не про доведену коректність.
- **Економія входу детермінована, виходу — ні.** Вхід зменшується на 1–38% залежно від рівня. Вихідні токени (7,8–9,0 тис.) коливаються від прогону до прогону, і shrink на них не впливає. Різниця в стовпчику «Усього» понад економію входу — це шум одного прогону; `--runs 3` (ще 10 запитів) усереднить її.
- **Чим довша відповідь, тим менша частка економії.** Тут вихід — 44% усіх токенів оригіналу. Тож −37,5% входу дають лише близько −16% від суми, якщо вихід не змінюється (11 556 − 7 217 = 4 339 токенів із 20 588). У грошах частка ще менша, бо вихідні токени зазвичай коштують у кілька разів дорожче за вхідні. Для задач на кшталт «прочитай багато, відповідай коротко» (eval якості, розділ 4) економія входу майже дорівнює економії всього запиту.
- **Змішаний проєкт стискався слабше за чистий Python** (−37,5% проти −76% на L3): половину контексту займають JS, HTML, CSS і README. Звідси режим `web` (див. вище).
- **Час відповіді** (216–522 с) визначала завантаженість безкоштовної моделі, а не розмір промпту: найдовший прогін (оригінал) був першим.
